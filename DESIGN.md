# Design

This is the living design record for Stellaris 15 Gen3 fan control. It explains why the project is shaped this way and records decisions that should survive individual code changes. Safety requirements in `AGENTS.md` take precedence if this document ever falls behind the code.

Last reviewed: 2026-10-11

## Goals

- Keep automatic fan control alive when the GUI crashes or PySide6 cannot start.
- Replace the untrustworthy OEM CPU-temperature input with the validated Ryzen `Tctl/Tdie` path.
- Keep hardware access and fan writes behind a small, elevated backend.
- Make every automatic decision predictable, conservative, and testable without live hardware writes.
- Preserve an immediate OEM Fan Boost fallback and recoverable curve backups.
- Run the same safety logic on Windows 11 and Ubuntu 24.04, with platform adapters only where hardware access, privilege, startup, and packaging differ.

## Non-goals

- Supporting laptops or OEM Control Center versions that have not been validated on the target hardware.
- Replacing or patching OEM program files.
- Reading CPU temperature from the OEM service, EC, MQTT, Core Temp, ACPI thermal zones, WinRing0, or TUXEDO Control Center.
- Depending on TUXEDO Control Center or out-of-tree kernel modules on Linux.
- Providing remote control. IPC is loopback-only.

## Process design

```text
normal-user frontend
        |
        | authenticated loopback JSON requests
        v
elevated backend ----> Ryzen SMN through PawnIO
        |              NVIDIA temperature through NVML in a killable helper process
        v
ControlCenterService --+-> one persistent OEM MQTT client (broker available)
                       `-> validated direct EC client (broker unavailable)
```

The backend owns the safety-critical state, automatic scheduler, temperature reads, and the only `ControlCenterService`. The frontend owns presentation and user confirmation. Backend validation is still authoritative because a UI check alone is not a security or safety boundary.

`ControlCenterService` selects OEM MQTT while the `GCUBridge` broker is listening and direct EC access only while it is unavailable. A method change closes the old client before opening the other. Direct writes use the installed Control Center 3.9.42.1 `ACPIDriverDll.dll` and `UWACPIDriver`, validate the exact DLL SHA-256 and EC project ID, reject malformed tables, write both fans under the existing service lock, and verify readback. They refuse to begin while the broker is present. This preserves the OEM path as the fallback without letting two writers intentionally operate at once.

Stopping `GCUBridge` clears all six RAM Fan 1.5 curve blocks and changes the OEM application/fan-subsystem state. The backend therefore caches the last complete OEM curve after successful OEM reads or writes. Direct activation reproduces the driver-call order observed from Control Center: assert application presence and fan-subsystem state, write the primary and mirrored fan-control bytes, then interleave CPU/GPU up thresholds, down thresholds, and duties. All 96 curve bytes and the control state are read back. An absent cache with cleared EC tables fails closed.

The direct fan locations are volatile EC RAM rather than an EEPROM/firmware update path. This is supported by the matching Uniwill implementation in TUXEDO's hardware driver, which names the same `0x0751`, `0x07C5`, `0x07C6`, and `0x0F00`-`0x0F5F` locations EC RAM and routinely rewrites the fan tables during initialization. The installed OEM DLL also exports distinct `WriteEC` and `WriteCMOS` functions; this application imports only `ReadEC` and `WriteEC`. This substantially reduces write-endurance concerns, but does not make arbitrary EC writes safe: the OEM firmware and Windows driver remain proprietary, so target validation, exact address restrictions, serialization, readback, and rollback remain mandatory.

The packaged `StellarisFanControl.exe` carries an administrator manifest and runs the PySide6 interface and backend controller in one elevated process. The interface uses an in-process client with the same synchronous dispatch boundary, while its one-worker pool keeps controller operations off the GUI thread. Closing the window hides it in the system tray and preserves the controller and Automatic scheduler. Only the dedicated Exit controls perform the confirmed 100% shutdown. The separate source entry points and authenticated loopback transport remain available for development. The application is packaged as a PyInstaller one-folder build installed under Program Files, so the PawnIO sensor module and DLLs sit beside the executable. A one-file build would unpack them into a per-launch `%TEMP%\_MEI*` directory, which temp cleaners can delete while the long-running process still needs them (see `ACCIDENTS.md`). On Windows the main window is cloaked in DWM from its show event until its first expose has painted and flushed, with a 1-second fallback reveal. Otherwise Windows displays the unpainted window, which stays white for a few hundred milliseconds while controller startup keeps the GUI thread busy.

Windows packaging resolves external DLLs with a temporary PATH containing only the selected Python runtime/virtual environment and Windows directories. On 2026-10-11 a Poppler ICU DLL with version-suffixed exports was incorrectly bundled as `icuuc.dll`, shadowing the Windows ICU API required by Qt and preventing startup. Source Qt tests could not detect that packaged dependency mismatch. The `--check-qt` entry-point switch therefore exercises the bundled frontend imports and an offscreen Qt event loop without importing a backend or accessing hardware, before any normal application launch.

## Automatic-control design

An automatic cycle reads both independent sensors, rejects unavailable, zero, malformed, or implausible values, and calculates a single target from `max(cpu_temperature, gpu_temperature)`. The same target is written to both fans.

The default curve is 30% at 35 C and 100% at 75 C. The endpoints can be adjusted from 0 to 100 C, but the hard 80 C safety cap still forces 100%. Targets are rounded to 5% steps and can never fall below 30% in Automatic mode.

Entering Automatic mode creates one backup before the first write. Later 15-second cycles reuse that protection instead of producing a backup every time. Changing to Manual stops future automatic cycles. Fan Boost pauses automatic writes while it is enabled.

## Sensor-loss emergency

The backend records the time of every successful, validated sensor read. A watchdog thread reads the sensors whenever no read was attempted in the last 5 seconds, in every mode. When no read has succeeded for 30 seconds, it enables EC Fan Boost, which reached 100% within about two seconds in the live test, whereas a 100% table ramps at about 1.7% per second. While the emergency lasts, Manual writes and turning Boost off are refused, and the EC Boost state is not mistaken for a user Boost. When readings return, Automatic mode resumes with the next validated target, which leaves Boost, or Manual mode restores the last written duties.

"Stale" means that no valid reading succeeded: errors, timeouts, zero, malformed, or implausible values, or a missing GPU. An unchanged value is not treated as stale, because the NVIDIA driver reports whole degrees that legitimately stay constant at idle, and both sources read live hardware registers rather than the frozen EC copy. A runtime-suspended Linux GPU is powered off and counts as a valid cold reading.

The sensor status has its own lock, which is never held while the state lock is acquired, so the watchdog cannot deadlock with the service-change path that reads sensors while holding the state lock.

Fixed after the 2026-10-16 three-agent review:

- The watchdog enters the emergency without consulting the cached Boost flag; `set_boost(True)` is idempotent. If the user's own Boost was already on, recovery leaves it on instead of restoring duties. Before, a stale cached flag disabled the emergency entirely.
- Every duty write leaves EC Boost on both platforms (Windows calls `set_boost(False)`, Linux rewrites the tables), so `apply_manual` clears the cached Boost flag. Before, Boost, then a Manual write, then Automatic left Auto idle and the emergency disabled until a GUI reload.
- `load_state` reads the EC under the state lock (state lock, then operation lock, the order used everywhere), so no write can land between the read and the cached Boost flag.
- Backups never block a safety write: the Auto write treats a failed backup as a logged warning (`backup_required=False`), and the stop/exit 100% write takes no backup. User Manual writes still report a failed backup without writing.

## Linux design

```text
normal-user tray GUI (PySide6)
        |
        | JSON over /run/stellaris-fan-control/backend.sock (peer-credential check)
        v
root systemd service ----> k10temp Tctl, nvidia-smi, RAPL package energy
        |
        v
LinuxFanService -> LinuxEcClient -> /dev/mem window 0xFE200000 (INOU EC RAM)
                \-> uniwill-laptop or tuxedo-drivers ctgp_offset sysfs (cTGP)
```

The BIOS N.1.61A15 DSDT defines `\_SB.INOU.ECRR`/`ECRW` as single-byte accesses to `0xFE200000 + address` under an AML mutex, with no mailbox protocol. A root process can therefore perform the same accesses through an `O_SYNC` `/dev/mem` mapping; the Ubuntu kernel enables `STRICT_DEVMEM` but not `IO_STRICT_DEVMEM`, and the window is not RAM. Accesses are paced at 6 ms like the OEM software and the mainline driver. Because each access is one byte, concurrent AML users cannot corrupt a transaction; the only shared state is the bit-level enable registers, which neither the firmware nor the mainline driver writes except `0x0741` bit 0, which both sides set. The DSDT SHA-256 is pinned like the Windows OEM DLL hash, so a BIOS update disables direct control until it is revalidated.

The register meanings match the mainline `uniwill-laptop` register map and TUXEDO's driver: `0x0741` bit 0 enables manual control, `0x0751` is the fan mode (`0x80` user, `0x20` high, `0x40` Boost), `0x07C5` bit 7 splits the CPU and GPU tables, `0x07C6` bit 2 enables the `0x0F00`-`0x0F5F` tables (end temperature, start temperature, duty per zone), `0x075B`/`0x075C` are the live duties, and `0x0464`/`0x046C` hold big-endian fan RPM. `0x07C5` bit 5 (`WHMS`) is forwarded to the NVIDIA driver as WhisperMode by the firmware, so Linux leaves it untouched. The Windows direct path still writes whole OEM-traced bytes there.

Linux writes the TUXEDO zone thresholds (0-115 C, then single-degree zones up to 131 C) with the same duty in all 16 zones, so the stale EC temperature selects a zone but cannot change the duty. A duty of 0% is written as raw 1, because raw 0 makes the EC run the fan at 30% for three minutes first. The live test on 2026-09-29 confirmed that the EC follows these tables with `0x0751` set to `0x00` or `0xA0`, and that `0x40` forces 100% immediately. Tables are written before the enable bits, only changed bytes are written, every write is read back, and a mismatch restores the previous bytes.

The service starts in Automatic mode on every start, persists only the Automatic endpoints and the GPU power offset in `/var/lib/stellaris-fan-control/settings.json`, and re-asserts the last requested fan state and cTGP offset every 15 seconds and on `SIGUSR1` from the resume hook. `SIGTERM` stops the IPC server and writes 100% to both fans before exiting. systemd restarts the service after any failure without a start limit. Writes are refused while `tccd` runs so that two controllers never fight.

When the NVIDIA GPU's PCI runtime status is `suspended`, it is powered off; querying it would wake it, so Automatic mode uses the CPU temperature alone. Otherwise the GPU reading remains mandatory and fails closed.

The GPU power limit uses the cTGP offset register `0x0744` (watts above the 115 W base, capped at 50 W and at the VBIOS maximum reported by `nvidia-smi`). The service writes the kernel driver's `ctgp_offset` attribute when `uniwill-laptop` or `tuxedo-drivers` provides it, and otherwise programs `0x0743`-`0x0746` itself the way those drivers do. Dynamic Boost is `0x0743` bit 1 with its 25 W amount in `0x0746`; neither kernel driver exposes a switch, so the service toggles the bit directly with TUXEDO's `db_enable` semantics (clearing the general-enable bit only when cTGP is off as well) and re-asserts the saved choice every 15 seconds, which also undoes the mainline driver's resume-time re-enable.

The NVIDIA driver applies these firmware limits only while `nvidia-powerd` runs; without it the enforced limit stays at the 115 W default. Measured on 2026-09-29 with `nvidia-powerd` running, `enforced.power.limit` was `min(115 + offset + 25, 165)` W and followed offset changes within 1.5 seconds without restarting the daemon. TUXEDO Control Center displays the same model (cTGP plus a "Dynamic Boost range" of `min(max - default - offset, 25)`) and relies on TUXEDO's driver packages to install and enable `nvidia-powerd` with its D-Bus policy. Ubuntu's own driver packages ship the unit only as documentation, so the installer does the same setup when the daemon is not running.

The lightbar is driven through the same window with the registers tuxedo-drivers uses for this SKU (the mainline driver has the code but does not enable it for `GMxZGxx`, a board name the Stellaris shares with the lightbar-less Polaris). `0x0749`-`0x074B` hold red, green, and blue from 0 to 36, and `0x0748` bit 7 runs the firmware's rainbow animation, which is also its power-on default. Color writes the three levels and then clears bit 7; Off writes 0/0/0 and clears bit 7, as tuxedo-drivers initializes it; Rainbow sets bit 7 only. The other `0x0748` bits and the battery-mode copy at `0x07E2`-`0x07E5` that the mainline driver also writes are left alone until validated. The EC does not keep these bytes across a reboot, so the service stores the choice, including the last color while Off or Rainbow is shown, and the 15-second check re-applies it after boot or resume. That check reads the four bytes and writes only when they differ. Because the lightbar may also forget its state while the bytes still match, the service additionally rewrites them every 15 minutes, at the first check after a service start, and whenever the user picks an option; such a routine refresh is not logged as drift. Until the user picks a mode, the service never touches the lightbar.

The GUI is the Windows GUI with platform switches: it adopts the service's mode instead of forcing Automatic, stores its preferences under `~/.config/stellaris-fan-control`, hides the GCUBridge button, and its **Quit** closes only the GUI. It never starts or elevates the service; while the service is unavailable it shows the reason and retries quietly.

## Windows telemetry and lightbar

Windows display snapshots add optional GPU `power.draw` through a separate NVIDIA query with a two-second timeout on its own display lane, so it never shares or delays the temperature lane; while a previous query is still running, the next one is skipped rather than queued. CPU package power uses read-only AMD RAPL MSRs `0xC0010299` (energy-unit exponent) and `0xC001029B` (32-bit package-energy counter) through the existing pinned PawnIO module. A serialized meter computes watts from unsigned counter deltas over monotonic elapsed time, including wrap. The first sample, changed units, read failures, intervals outside 0.5-30 seconds, and values above 150 W produce an unavailable value. Reads less than 0.5 seconds apart reuse the previous power value. Both MSRs are sampled under the existing global PCI mutex, and the transport rejects every operation/register except these reads and the existing thermal-register read before opening the device. The module pin, driver, and temperature decoding are unchanged. Read-only sampling on 2026-10-11 reported 6.5-6.9 W on the target laptop; comparison with Linux RAPL remains pending.

The Automatic cycle and sensor watchdog never issue power queries. Missing, non-finite, malformed, negative, or implausible power values are displayed as unavailable and do not affect temperature validity. CPU and GPU power failures are independent. Direct EC telemetry reads big-endian fan RPM at `0x0464`/`0x046C`; unavailable or implausible RPM does not hide valid fan-duty telemetry. OEM MQTT RPM is displayed only if its telemetry provides the existing RPM fields.

The Windows lightbar uses the Linux-validated AC-power register meanings through the existing hash-validated OEM DLL. It is available only in Direct EC mode; no second EC or MQTT client is created. `ControlCenterService` serializes it with fan operations, refuses while the OEM broker runs, and the direct client repeats that refusal before every write and rollback byte. Only RGB `0x0749`-`0x074B` (0-36) and `0x0748` bit 7 change. Color bytes precede the animation bit, unrelated bits and the battery-mode copy are preserved, and failed readback attempts to restore the previous written bytes. If OEM ownership returns, rollback also stops to avoid fighting the OEM writer. Pure validation is shared with Linux.

Windows cTGP uses the same serialized Direct EC client and the Linux-validated register encoding. GPU control additionally checks registry board `GMxZGxx`, SKU `STELLARIS1XA03`, BIOS `N.1.61A15`, EC project `0x10`, and universal-control flag `0x078E` bit 6. Each write requires a fresh NVIDIA query with the exact 115 W base and a maximum from 115 to 165 W; missing or malformed limits refuse writes. The service caps the offset at the smaller of 50 W and VBIOS headroom. It writes offset, TPP `0xFF`, and Dynamic Boost amount 25 before changing only general/offset/boost enable bits. Readback mismatch attempts restoration of only written GPU bytes, and the OEM broker blocks every forward or rollback byte. Fan and WhisperMode bytes are not changed. The user choice is saved atomically in `gpu-power.json` and maintained every 15 seconds on the existing peripheral thread, with error handling independent of lightbar maintenance. Without a choice, startup and telemetry perform no GPU writes. The GUI displays NVIDIA's enforced limit separately and warns if it is below the requested sustained limit.

The user's OEM 4.9.47.13 ZIP was extracted statically on 2026-10-11, without executing its installer, service, or DLLs. Service metadata confirms the four cTGP addresses, but also aliases them to fan PWM on other platforms, hence the extra platform gates. Protected setter bodies prevent recovering write order, bit masks, and possible additional NVIDIA calls. The native libraries expose a separate WhisperMode path and NVIDIA profile preferences; those observations do not justify private driver setters or fan-protocol changes. The downloaded ACPI DLL has a different hash and remains unused. Read-only target checks found the expected board/BIOS, inactive cTGP bytes, and NVIDIA 115 W base / 165 W maximum / 120 W enforced.

The owner then explicitly authorized Windows tests at 115, 130, and 165 W. With Fan Control exited normally and both fans at 100%, a single Direct EC client wrote offsets 0/15/50 with Dynamic Boost off and sampled NVIDIA for 12 seconds per step, without stress load. NVIDIA followed all three limits. All four original EC bytes were restored and verified afterwards; NVIDIA's final reported limit was 115 W, rather than its pre-test 120 W. Register restoration therefore does not promise restoration of a previously observed driver limit. This validates sustained limit changes through the existing driver on this laptop, but does not validate Dynamic Boost toggling, saved-choice repair after restart/resume, or full-ceiling thermal stability.

An authorized 60-second GPU-only CUDA load on 2026-10-11 maintained 98-99% utilization after startup. While the owner changed the slider, NVIDIA samples showed limits from 115 to 155 W, then 165 W during cooldown. Peak sampled GPU draw was 112.95 W, GPU temperature 63 C, CPU temperature 57 C, and both fan duties reached 75%. The load ended normally without a temperature abort. This workload did not reach the selected power ceiling and does not validate sustained 165 W draw or long-duration thermal stability. The local read-only monitor used the existing CPU/NVIDIA sources and hash/project-gated EC fan reads; the installed Automatic controller remained the only fan writer. CUDA kernels stayed below 31 ms. The initial 60-second run achieved only 56-73% utilization; increasing the bounded kernel work removed most launch overhead for the subsequent run. Reports and the one-off helper remain ignored under build/qa/gpu-stress-*.

A subsequent authorized FurMark 2.10.2 OpenGL test on 2026-10-11 ran on the RTX 3080 Laptop GPU for 60007 ms at 1920x1080, ending normally. The owner changed the limit during the test: sampled NVIDIA limits were 145, 160 and 165 W, so this was not a fixed 155 W run. At 160 W the driver reported up to 159.68 W average draw and 161.09 W instantaneous draw with software power capping active; at 145 W it initially drew about 144.5 W. Peak sampled GPU/CPU temperatures were 65/58.75 C, and both fan duties reached 80%. Software thermal capping became active at a reported core temperature of 59 C and later reduced draw to roughly 96-101 W and graphics clocks to about 1065-1080 MHz, even with a 165 W limit. Hardware thermal and external power-brake flags were inactive. Memory temperature and T.Limit were unavailable; the post-test driver reported an 87 C target and 105 C maximum operating temperature. The source of software thermal capping is unresolved, and sustained ceiling power is not validated.

FurMark was downloaded as a portable ZIP from the official Geeks3D endpoint, matching its published SHA-256 `27AB2E723E2E65DF720BCAFEA681D2104744EDA4A1E0A0374D7E61EAA820E63B`. Its internal GPU-monitor plugin was disabled; the local read-only monitor recorded NVIDIA clock-event reasons and existing CPU/EC telemetry, retaining temperature aborts and a 75-second process deadline around the built-in 60-second test. Fan Control remained the only fan writer. The earlier original CUDA workloads were insufficient for power-ceiling validation, despite high utilization; an improved finite, independent FMA workload peaked at 134.84 W.

A later run configured for 300 seconds exited normally after 176162 ms; no monitor temperature abort occurred, and the reason for early normal exit was not established. It does not count as a completed five-minute test. Selected limits changed between 115/140/145/165 W; peak sampled draw reached 164.83 W, GPU temperature 72 C and CPU temperature 65.875 C. The final loaded sample drew 139.4 W at a 140 W limit with software power capping active and software/hardware thermal and power-brake flags inactive. Both fan duties reached 100%. This confirms transient 165 W operation and later near-ceiling 140 W operation, without establishing the earlier software thermal-cap cause.

On Windows, an amber warning icon beside the control-method badge (Direct EC or OEM MQTT) appears when NVIDIA reports software thermal throttling. The tooltip explains that GPU or memory thermal limits may be reducing performance. It refreshes with the existing approximately 10-second sensor telemetry; inactive, unavailable or failed telemetry clears the icon. This is display information and does not alter fan targets, power settings or thermal protections. The optional GPU power query includes `clocks_throttle_reasons.sw_thermal_slowdown` in the same bounded NVIDIA process. Only exact Active/Not Active values become true/false; other values remain unknown. Power parsing and the thermal flag are independent, so unavailable watts can still show the warning. Neither the Automatic cycle nor the sensor watchdog queries this field.

GPU slider presses cancel pending debounce timers, and both scheduling and application refuse while the handle is held. Release applies the final value once; keyboard/wheel actions retain their debounce. This shared GUI behavior applies to Windows and Linux.

The backend stores only an explicitly selected mode and the last RGB choice in `%LOCALAPPDATA%\StellarisFanControl\lightbar.json`, independently of GUI preferences. Invalid or missing settings leave the lightbar alone. A dedicated backend maintenance thread checks the choice every 15 seconds and rewrites only changed bytes, with a forced refresh after startup, after returning from OEM control, and every 15 minutes. Resume is covered by the next periodic check; it does not introduce fan-table drift repair or change Windows fan-write semantics. Errors remain visible in the sensor warning line, and the thread survives exceptions. Closing to tray preserves maintenance; controller shutdown joins the thread before closing the service. The GUI cancels pending lightbar changes when capabilities become unavailable.

These Windows extensions have fake-EC, mocked NVIDIA, persistence, and offscreen GUI coverage. Live Windows validation of RPM, lightbar AC/battery behavior, resume, and OEM transitions is still required.

GPU power maintenance errors remain in the shared warning line until the backend reports recovery, even when sensor telemetry succeeds. Emergency, sensor, and fan faults take priority over GPU power errors; lightbar errors follow them.

## Concurrency design

- The backend process lock allows one backend per user runtime directory.
- `ControlCenterService` is a process-wide singleton with a serialized operation lock.
- Automatic scheduling runs in the backend and does not depend on the Qt event loop.
- A sensor lock prevents overlapping PawnIO and NVIDIA reads.
- Automatic state is checked again after sensor acquisition so a late Manual-mode or Fan Boost change prevents the pending write.
- The GUI worker pool has one thread and skips timer work while an operation is already active.

## IPC design

The backend binds an ephemeral IPv4 loopback port and writes its host, port, and random token to `%LOCALAPPDATA%\StellarisFanControl\backend-endpoint.json`. Requests and responses are newline-delimited JSON with a 64 KiB limit. Application control does not use MQTT; the OEM MQTT connection is a hardware-specific implementation detail owned exclusively by the backend.

Current commands are `ping`, `load_state`, `read_telemetry`, `apply_manual`, `set_boost`, `set_gpu_power`, `set_dynamic_boost`, `read_lightbar`, `set_lightbar`, `set_oem_service`, `prepare_exit`, `set_mode`, `configure_auto`, `frontend_heartbeat`, `frontend_detach`, and `show_frontend`. Windows GPU power and lightbar commands require Direct EC; capabilities disable them during OEM MQTT use. Service changes and exit preparation are rejected unless the frontend includes the confirmation marker after the user accepts the corresponding modal prompt. A confirmed exit serializes a 100% write to both fans, stops Automatic scheduling only after that write succeeds, and leaves the window open on failure.

The token prevents unauthenticated requests that cannot read the endpoint file. This is local process authentication, not encryption and not a claim that the current-user account is isolated from its own processes. IPC hardening work belongs in `TODO.md`.

## User-interface design

The window is a wide three-column layout: Automatic controls on the left, Manual controls in the middle, and sensor values on the right. A two-state mode toggle selects Automatic or Manual. Manual input commits automatically after a short debounce; its optional mirror toggle copies whichever fan target was changed to the other fan before the shared pair is submitted. A distinct top-right Exit button avoids conflating window hiding with application shutdown, and the adjacent badge always reports OEM MQTT, Direct EC, or the initial detection state. The inactive control section is disabled and covered by a translucent overlay; telemetry, Fan Boost, and the confirmed `GCUBridge` start/stop button remain available in both modes. The service transition is serialized by the backend with fan operations, waits for the broker state to match, and allows the OEM shutdown cleanup interval to finish before direct EC use.

Packaged preferences are written atomically to `StellarisFanControl.json` beside the executable. Only validated Automatic endpoints, Manual CPU/GPU targets, and the mirror toggle are persisted. The control mode is intentionally not persisted: every launch starts Automatic only after the backend has loaded the active curve and both independent temperature paths remain subject to fail-closed validation.

The automatic curve graph visualizes the configured temperature endpoints and the fixed 80 C full-speed cap. CPU and GPU temperature gauges are separate from the reported CPU and GPU fan-duty gauges.

The **Lightbar** button opens a separate window with three options, Color (red, green, and blue sliders), Rainbow animation, and Off, each in its own panel with a checkbox. The checkboxes are exclusive like radio buttons: exactly one is ticked, clicking another switches to it directly, and the color sliders are grayed out unless Color is ticked. Picking an option applies it at once, and color slider changes apply after a 300 ms pause. The window reads the service's state each time it opens. On Windows the button is enabled only during Direct EC control.

All styling lives in `frontend/stellaris15gen3.css`; Python code supplies structure, state, and custom-widget painting.

The always-available Start minimized checkbox persists a boolean `start_minimized` preference, defaulting to true when missing or invalid while preserving an explicitly saved false value. It only changes initial window visibility on the next launch. With a system tray available the window stays hidden; without one it is minimized on the taskbar so it remains accessible. Tray activation and second-instance activation still restore the window. Automatic scheduling is independent of this preference.

## Release distribution

Tagged `v*` pushes build Windows x64 release archives through GitHub Actions. The build job has read-only repository permissions and skips PawnIO driver installation while retaining the pinned module hash check. A separate publish job receives write permission only for tagged releases after the build and mocked tests succeed. Branch dispatches produce artifacts without publishing.

The same installer accepts a local `dist` executable or the executable at the root of an extracted release archive. It prepares PawnIO and installs into Program Files, preserving preferences and registering an interactive, highest-privilege sign-in task. Startup therefore remains independent of source/download folder moves. Neither packaging nor installation launches Automatic mode. Release checksums detect download corruption; the application remains unsigned.

## Experimental firmware MUX selection (2026-10-15)

backend/gpu_mux.py is independent of fan EC transport: the official MUX switch writes the AMD OemDisplayMode byte at UniWillVariable + 0x62. The backend owns firmware access, exact platform/DSDT and variable-format checks, lock, pre-write backup, concurrent-change refusal and full verification. It performs no periodic/startup/recovery writes and never reboots. It does not blindly roll back a whole NVRAM blob on verification failure. The GUI uses existing authenticated IPC and serialized workers, with a separate panel next to GPU power and two confirmations. The final confirmation and backend require exactly YES DO IT. Saved mode is distinguished from the active display route. See cc_analysis/nvidia-optimus.md for evidence and unvalidated target behavior.

### Linux password and the efivarfs immutable flag (2026-10-15)

The kernel marks non-standard efivarfs variables, UniWillVariable included, immutable at every boot, so the first Linux design needed a manual `chattr -i` before each save. The owner decided instead: the root service lifts the flag itself, but only inside a confirmed save, behind an administrator password. After YES DO IT, and only when the saved mode differs from the request, `FirmwareMux.set_mode` calls an authorizer before the backup and outside its lock. On Linux that is `backend/linux_polkit.py`: `pkcheck --allow-user-interaction` for action `io.github.salihmarangoz.stellarisfancontrol.set-gpu-mux` (`auth_admin`, never kept), subject `pid,start-time,uid` of the kernel-reported socket peer, with the start time read when the `set_mux` request arrives, so a PID reused after that cannot inherit it. `PeerCredentialServer.authorize` records that peer in a thread-local, because each IPC request runs authorize and dispatch in its own server thread; without a recorded peer, or if the requester is already gone, the authorizer fails closed. Root clients are not asked. Denial, a cancelled dialog, a missing agent or rule, or no answer within 150 s refuses the save before any backup or write. The password covers exactly the firmware state it was asked for: the locked write section refuses if the variable differs from the blob seen at the pre-check. A three-agent review on 2026-10-16 found that without this, a concurrent request whose pre-check saw no change (and so asked nothing) could write after another, authorized save. On non-Windows hosts `FirmwareMux` also refuses any save without an authorizer, so the password cannot be lost by a caller that forgets it; tests opt out explicitly with `require_authorization=False`. `LinuxFirmwareTransport.write` then clears `FS_IMMUTABLE_FL` with `FS_IOC_SETFLAGS` (what `chattr` and `efibootmgr` do), writes, and restores the original flags in a `finally`; a failed restore is logged and heals at the next boot. The GUI waits up to 180 s for this request. Windows is unchanged: its backend already runs elevated after UAC.

Validated on the target laptop on 2026-10-16 (owner-run, read back by an agent): a Cancel and a wrong password each left the variable untouched (polkit logged the failures); a correct password gave a one-shot authorization and changed only data byte 0x62, once with the immutable flag already cleared by hand and once on a fresh boot with the flag set, which was set again after the write; and the next boot followed the saved mode both ways (Hybrid, then dGPU).

## Windows OEM ownership checks without connection timeouts (2026-10-16)

The broker is at IPv6 ::1 port 13688. A failed socket connection took about 201 ms on the target, and the required per-byte ownership guard multiplied that by roughly 100 writes per fan update. The serialized controller also made Boost wait behind those transactions. `backend/windows_broker.py` instead queries `GetExtendedTcpTable` with Windows AF_INET6 and TCP_TABLE_OWNER_PID_LISTENER, matching the loopback address or an IPv6 wildcard listener. Only the System32 API binding is cached; each guard reads a fresh table. API failures, malformed table sizes/counts and excessive growth raise instead of reporting broker absence. The non-Windows socket path is unchanged. Keep all existing EC write ordering, per-byte refusal, verification, rollback and serialization; do not parallelize hardware writes or cache ownership absence to improve latency. Target results and the explicit 50% Manual-test floor are recorded in cc_analysis/windows-direct-ec-latency.md.

## Bounded hardware operations and output-failure recovery (2026-10-16)

`shared/bounded_operation.py` provides a single in-flight slot, no backlog, bounded caller waits and discarded late results. The controller uses independent temperature (4 s), NVIDIA power-telemetry (4 s) and EC (8 s) lanes. The temperature NVIDIA query is killed after 3 s (on Windows the NVML helper process, on Linux the `nvidia-smi` subprocess), so a stuck query frees the temperature lane before the next caller's deadline; on 2026-10-17 the earlier 2 s lane, shared with the power query, was the suspected cause of intermittent sensor-loss Boost under load. Native work runs on a daemon worker; timing out never terminates the thread or frees its ownership slot. Controller locks therefore no longer wait indefinitely for native work. The watchdog checks freshness before sampling and sensor success is recorded only for an accepted in-deadline result. Optional Windows CPU power sampling shares the temperature lane so it cannot create concurrent PawnIO operations; GPU power never does.

Every controller service operation and Linux maintenance uses the EC lane, retaining the service's existing operation lock and per-byte hardware/ownership protections. Ordinary contention waits only within the same total deadline; an expired waiter is never run later. An abandoned EC call retains the slot through a guarded Boost attempt after the original call actually finishes. This orders any late lower target before fallback, while refusing new work instead of queuing a stale user command. A permanently hung driver cannot deliver Boost; the snapshot and GUI explicitly show unconfirmed safety. No driver-thread termination, hardware bypass or replacement controller is used. Closing the service and joining peripheral maintenance also have bounded waits.

Fan-target and Boost failures latch a separate output error and attempt guarded Boost immediately. Boost refusal/errors remain visible and are retried by the sensor watchdog. Lower Manual targets and Boost-off are blocked while the fault is latched. A verified fresh Auto write or an explicit verified Manual 100/100 write clears it; successful Boost alone and fresh sensors alone do not. Safety Boost is not cached as the user's own Boost by load_state, so Auto recovery remains schedulable. Each new stale-sensor episode reasserts Boost even if the cached user flag was already on. Existing sensor-only Manual recovery restores the previous targets. Fixed Manual targets intentionally do not scale with valid high temperatures.

The packaged in-process client has its own single-flight request lane and honors request_timeout (default 15 s), including existing longer shutdown/service/MUX deadlines. GUI completion/failure therefore releases busy controls after the deadline; a rejected request never waits in a queue. A stalled in-process client advertises can_restart=False, preventing the frontend watchdog from starting another hardware controller. The GUI reports unfinished requests without pretending they were cancelled or succeeded. Normal Exit still requires a successful 100/100 write and remains open on failure. See cc_analysis/windows-safety-review-2026-10-16.md for fault-injection and hardware-test scope.

## Windows NVIDIA helper process and EC write skipping (2026-10-18)

An idle trace on 2026-10-18 put the installed app at about 19% of one core, almost all of it busy-waiting inside `UWACPIDriver.sys`. Each unchanged Automatic cycle rewrote and re-read the complete Direct EC table: about 100 writes, each with its OEM ownership check, and roughly 200 reads. `DirectEcClient._write_curve` now compares a fresh read of the table and the four mode bytes with the target and writes nothing when they already match; any difference still runs the full ordered write, readback and rollback. `curve()` hands its table read to the write that follows within the same operation instead of reading the table twice; any EC write, or 1 second, discards that read. `set_boost` likewise skips writes only when all four mode bytes already match. An unchanged cycle therefore costs about 100 reads and no writes. A second step goes further: `uniform_duty_verified` confirms an unchanged Auto target from only the 32 duty bytes and 4 mode bytes, for up to 5 minutes after a complete verification with no EC write in between. With one duty in all 16 zones, the 64 temperature thresholds cannot change fan speed, so a threshold drift is repaired at the next complete check. Any duty or mode mismatch, a new target, a backup, an EC write (including lightbar or GPU power), or a reconnect falls back to the complete check immediately. A restored OEM mode never qualifies. The Boost-off step after a Direct EC table write was dropped because the table write already verifies the same mode bytes. The remaining ~9 ms per byte is a delay inside the OEM driver; see `cc_analysis/windows-ec-driver-busy-wait.md`.

`backend/nvidia_helper.py` replaces the `nvidia-smi` launches. The backend keeps one helper process per lane (temperature, and power/limits telemetry), so a slow telemetry query never delays a temperature read. Each helper keeps NVML initialized and answers one JSON line per request over its pipes. A query that misses its deadline kills the helper through a kill-on-close job object, and the next query starts a new one; a helper that is still starting is left alone up to 15 seconds. NVML runs only in the helper because a hung driver call inside the backend could never be cancelled and would leave the temperature lane blocked until restart. The helper uses only the standard library: source mode runs it as `python -I backend/nvidia_helper.py`, and the packaged executable starts itself with `--nvidia-helper` before any Qt or hardware import. It loads `nvml.dll` from `System32` by absolute path and calls only read-only NVML functions.

Before every query the helper reads the single NVIDIA display device's `DEVPKEY_Device_PowerData` through SetupAPI. The PnP manager answers from its own records, so the GPU is not woken. D3 means powered off: the helper answers without calling NVML, the temperature reading carries `gpu_powered_off`, and Automatic mode uses the CPU temperature, so both fans get the CPU target, as on Linux. Any other state, or a failed check, queries NVML as before and keeps the fail-closed rule. Whether this PnP state tracks the laptop's runtime D3, and whether the helper's open NVML session keeps the GPU from powering off, are not yet validated on the target.
